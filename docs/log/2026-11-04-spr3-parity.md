# 2026-11-04: `W3SPR3` and ST3's `CALC_USTAR` at bit parity

First routine of ST3 (WAM cycle 4): the mean wave parameters `W3SPR3` and, with its own ledger row, the `CALC_USTAR` of
`w3src3md` (not the ST4 one of `sin4.rs`). Status `routine` (`rust/port_report/W3SPR3.md`). Nothing ran on a GPU. No
timings. `W3SRCE` does not call it yet.

## Reading the compiled code first

`gdb`'s `disassemble` of `__w3src3md_MOD_w3spr3` in the reference (the image has no `objdump`): three scalar `powf` calls per
band, `CALC_USTAR` called not inlined, `MAX` as `fmaxnm`, no fused instruction. ww3-gpu read the x86 object and found that
`-O3` drops `MAX(1.E-7, FMEAN)` in the `ELSE` branches; the aarch64 object keeps it, as the source has it. `ALFA` is
computed and stored and never read.

## What the default case does not reach

`ww3_ts1` reaches neither a zero wind (`U` is 0.001 at its calmest), nor `TAUW > TAUWMAX` except in a storm, nor the
last `TAUT` columns, nor a wind-sea energy below `1.E-7` with a mean frequency above it. The entry pokes of
`regtests/capture/spr3.py` write those inputs into the real routine. The first version of the poke missed three branches:
the `.OR.` of the `FMEANWS` test, the 0.001 threshold of `CHARN`, and the first term of the `TAUT` interpolation, whose
weight `DELJ2` is exactly 1 at an integer wind. Fault runs found them, and the poke grew a spectrum confined to the top
bands (`SIG > 1`, where `FMEANWS` is larger than `EMEANWS`), two breezes and a gale at 37.3 m/s.

## A harness that ran a stale build

The fault harness rewrote `spr3.rs` a minute apart and relied on cargo noticing. One fault reported the number of the
fault before it, 12 832 differing values where a rerun gave 50. The harness now removes the crate fingerprints before each
run; all 40 results above are from that version.

## Not done

`W3SPR3` is not called from `W3SRCE`; `moddef.rs` reads `switch_chaceon_shrd`'s layout only, so no model run uses ST3. The
`IND` and `DELI1` clamps of `CALC_USTAR` cannot act: `XI` is at most 133.75. `docker/Dockerfile.ptx` is untracked in the
main checkout, so `just ptx` fails in a fresh worktree until it is committed.
