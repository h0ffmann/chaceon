# 2026-11-04: `W3FLX4` at bit parity: Hwang's drag, its 50.33 m/s cap and `CDFAC`

`W3FLX4` (`model/src/w3flx4md.F90:105-231`), the drag coefficient of Hwang (2011) for the `FLX4` switch, is translated into
`ww3-kernels` with SPIR-V and PTX entry points and no new `ww3-libm` function. Status `routine`
(`rust/port_report/W3FLX4.md`). Nothing ran on a GPU. No timings. It is not called from `W3SRCE`.

## What the captures reach that the default run does not

`ww3_ts1` runs at 12 m/s, far below the cap at 50.33 m/s. Winds of 55 and 120 m/s take the cap branch, `CDFAC` (the module
variable `FLX4A0`) is set by `&FLX4 CDFAC=` in the case's namelist, and the poke writes `U10` at the routine's entry (50.33 as
an `f32`, the float below it, 0, negative, 10^6), which is what catches `>=` against `>` in the cap test.

## What a fault run found about the fault, not the code

Two of my first fault edits were no faults: one replaced the first `8.058 +` in the file, which is in a comment, and one a
literal that rounds to the same `f32`. They were redone on the code line and caught. A fault that changes nothing needs a look at
the edit before it is called a blind spot (`.claude/skills/ww3-port/SKILL.md`).

## The NaN sign, again

As in `W3FLX1`, `-0.4/SQRT(CD)` is `-(0.4/SQRT(CD))` and the `poke` with `U10 = -20` makes `CD` negative. On the host,
`black_box` already holds the quotient, so `expf(-q)` still matches; in SPIR-V that plain form differs in 38 of 500 `Z0`
NaN signs, and the integer sign flip fixes it. The fault was built and replayed in SPIR-V.

not called from `W3SRCE`.
