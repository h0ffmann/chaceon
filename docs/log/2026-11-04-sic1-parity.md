# 2026-11-04: `W3SIC1` at bit parity, and a NaN sign that two optimisers move

`W3SIC1`, the uniform-rate ice damping of `IC1`, is ported to `routine` (`rust/port_report/W3SIC1.md`). Nothing ran on a
GPU. No timings.

## `ww3_ts1` has no ice

`W3SIC1` runs only when `INFLAGS2(4)` is set and `ICE > 0`, and stops the run without `INFLAGS2(-7)`. The case's
`ww3_shel.nml` gets homogeneous `ICE` and `IC1` input from `regtests/capture/ice1_shel.sh`, so the real routine runs with
real arguments. Inputs the case cannot produce (`ICEP1` negative, NaN, Inf, subnormal; `A` NaN or Inf) are poked at the
routine's entry, as for `W3SIN4`.

## A NaN sign

The disassembly says `-2.*CG*WN_I` is `-((CG+CG)*WN_I)`. The first translation, `-2.*c*ice`, was bit-identical on every
finite input and differed on 61 344 values of the poked capture, all in the sign bit of a NaN: `fneg` flips it and a
product by `-2` keeps it. After the translation followed the disassembly the host matched, but SPIR-V differed on the
same 61 344 values: spirv-opt folds `-(a*b)` into `(-a)*b` (`OpFMul -2.0 c` in the module), and NVPTX does the same
(`mul.rn.f32 ..., 0fC0000000`). A float negation can be moved because the value is unchanged, and a NaN is the only
thing that notices. The kernel now flips the sign with an integer xor, which neither folds, and SPIR-V is 0 differ. It
is a NaN `ICEP1`, which no run produces; the capture reaches it only by poking. A routine that negates a product and
can see a NaN may need the same.

## A batch hides a wrong `CG` offset

In `ww3_ts1` every call has the same `CG`, so dropping `k_off` in the batch layout changed nothing on any one capture. A
file joining captures of 2500, 8 and 20 m (`regtests/capture/sic1_mix.py`) caught it: 3 382 572 values.
