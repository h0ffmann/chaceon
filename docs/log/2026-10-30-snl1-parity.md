# W3SNL1 at parity on the host and as SPIR-V

2026-10-30, agent session `cd86e8f5` for the owner; no issue. Branch
`goal/cd86e8f5-5180-snl1-parity`. Results and fault runs: `rust/port_report/W3SNL1.md`.

## Question

Can the next routine by wall time be ported to Rust on the GPU with its parity shown, with no Fortran
written, no Rust test, and no device run?

## Result

- gdb captured every `W3SNL1` call of `ww3_ts1`. Rust matched all 8200 calls, 14 169 600 values, on
  the host and as compiled SPIR-V on lavapipe, and all 30 163 table values (v).
- `expf` equals glibc 2.36 on all 2^32 inputs without a fused multiply-add (v).
- Both compilers built the kernel on the owner's Mac, Rust-CUDA inside linux/arm64 Docker (v).

## What went wrong on the way

- **The first fault run proved nothing.** The last bit of an `f64` coefficient never reached `f32`,
  and "0 differ" was read for a moment as a failed control. A larger fault did reach it.
- **A deep case hid a branch.** With `expf` wrong, 2500 m still matched, because `EXP(X2)` vanishes.
  The 20 m and 8 m runs exist for that.
- **The first capture was 518 MB.** A gdb temporary breakpoint is not deleted when `stop()` returns
  `False`.
- **Rust-CUDA, in order:** `libzstd-dev` missing; newer `glam` gates `UVec2`, so `just ptx` pins
  0.30.9; LLVM 21 bitcode is refused by libNVVM below sm_100, so the H100 and RTX 4090 need LLVM 7;
  stale LLVM 21 artifacts then failed to parse until `target/` was cleared.
- **rust-gpu:** closures capturing locals by reference failed `spirv-val`.

## What it changes

The next routines follow the same path: capture, translate, replay, fault run. Without a device run
there is still no statement about a real GPU ⚠.
