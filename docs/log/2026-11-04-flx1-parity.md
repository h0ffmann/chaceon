# 2026-11-04: `W3FLX1` at bit parity, and a NaN sign that LLVM rewrites

`W3FLX1`, Wu's (1980) wind stress for the `FLX1` switch, is the smallest routine of Batch 7: three lines of arithmetic, one
`sqrtf` and one `expf`. Status `routine` (`rust/port_report/W3FLX1.md`). Nothing ran on a GPU. No timings.

## What the poke found

`ww3_ts1` gives only four wind speeds, all positive, so the captures never take `sqrt` of a negative number. The
`poke` variant writes other `U10` at the routine's entry, as `sin4.py` does for `USTAR`. The first run differed in 62 of 500
`Z0`, all NaN: ours `0x7fc00000`, the reference `0xffc00000`. Two things stack. Fortran reads `-0.4 / SQRT(CD)` as
`-(0.4 / SQRT(CD))`, so gfortran divides and then negates (`fdiv`, `fneg`), and a NaN quotient changes sign; the first translation had
`-0.4 / sqrtf(cd)`, equal for every non-NaN. Then LLVM turned `-(a / b)` back into `(-a) / b` in the host build, and
`spirv-opt` did so in SPIR-V, each restoring the wrong sign. `black_box` stops it on the host and rust-gpu ignores it, so the
kernel also flips the sign as an integer. A NaN only arises for `U10 < -12.3` m/s, never in a model run, but the bits are equal now
and the fault run with `black_box` removed catches it.
