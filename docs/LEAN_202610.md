# Lean in chaceon: what it is here, and what it is not

2026-10-31. Lean 4 checks a statement about mathematics or about a model of a program. In this repository it
is a third kind of evidence next to `cmp` and captures. It does not replace WAVEWATCH III® (WW3), it does not
check Rust, and it cannot show that a Rust routine equals a Fortran one. Pins are in [`VERSIONS.md`](../VERSIONS.md);
the proof is [`lean/Chaceon/Division.lean`](../lean/Chaceon/Division.lean); `just lean` builds it in Docker (Lean is
never installed on the host) and prints the axioms of each theorem.

## Three kinds of evidence

| Evidence | Says | Cannot say |
|---|---|---|
| `cmp` on whole runs (ADR-0005) | the output files of this run, on these inputs, are byte-identical | anything about an input not run |
| Captures and replays (ADR-0007) | a routine returns the same bits for every call the reference made in the captured runs, and a fault in the input is caught | anything about a call the runs did not make |
| A Lean proof | a stated fact holds for every input the statement allows | anything the statement does not state, including whether the statement is the one we meant |

`cmp` and a capture measure the code against the reference over the inputs that ran. A proof covers all
inputs of one fact, and nothing else. The two meet where a run cannot enumerate: there are 2^64 pairs of `f32` operands, so no run covers them, and the fact the division widening needs is proved instead.

## Lean and Fortran

Lean checks statements about mathematics or about a model. No usable formal semantics of Fortran, or of what
gfortran `-O3` makes of it, exists ⚠ (not found in a search; absence is not shown). So "the Rust equals the Fortran" is not
a theorem we can state, and the reference stays the Fortran's files, compared by `cmp`. Lean's value is on the other side:
it can catch a defect a port reproduces faithfully, which `cmp` cannot see because both sides agree. A positivity
or conservation property of a scheme, proved on the reals, would be such a check.

## Lean and Rust

Rust's types already give disjoint mutable access and memory safety. Lean states numeric properties. Rust runs on
the GPU; Lean's `Float32` does not replace `f32`: Lean's reference says `Float` and `Float32` are wrappers
around logical models, operations such as `sin` are opaque and do not reduce in the kernel, and the model is not meant
as the base of a floating-point library (v, Lean reference, "Floating-Point Numbers", read 2026-10-31). This pilot
therefore proves a fact on `ℚ`, the rationals, and argues from it to the device.

Aeneas translates safe Rust to a pure Lean model, and could state a kernel's loop and index facts against the
source. Its README says it handles "a subset of safe Rust" and does not mention floats (v, README, read 2026-10-31).
That floating-point support is unfinished is my reading of that silence ⚠: I found no statement either way. chaceon's
kernels are `#![no_std]` safe Rust over `f32`, so the float gap would matter first.

## What this pilot proved

**The fact.** `spirv_exact` rewrites each `f32` division `a/b` to `f64`, divides, and rounds to `f32` with
`OpFConvert`, because Vulkan allows 2.5 ULP in `OpFDiv`. Claim: the result is the correctly rounded `f32` quotient
even with a 2.5 ULP error in the `f64` division, for a quotient in the normal range.

Set `a = A·2^ea`, `b = B·2^eb`, with integers `0 < A, B < 2^24`. The scale `2^(ea-eb)` is common to `q = A/B` and
to every neighbouring midpoint, so it factors out; a midpoint becomes `m = M / 2^t` with `M` odd,
`2^24 <= M < 2^25` and `t` an integer, possibly negative. The Lean statements (all over `ℚ`, `mid M t = M / 2^t`):

| Theorem | Statement |
|---|---|
| `no_tie` | `0<A<2^24`, `0<B`, `2^24<=M`, `M` odd: `A/B ≠ mid M t` |
| `margin` | the same, with `B<2^24`, `M<2^25`: `mid M t / 2^49 <= |A/B - mid M t|` |
| `same_side` | `0<q`, `0<m`, `m/2^49 <= |q-m|`, `|r-q| <= 5/2 · 2^-52 · q`: `r < m ↔ q < m` |
| `closer_lo` | `lo<hi`: `|x-lo| < |x-hi| ↔ x < (lo+hi)/2` |
| `rounds_same` | for `lo=(M-1)/2^t`, `hi=(M+1)/2^t` and `r` within `5/2 · 2^-52` of `A/B`: `r` is closer to `lo` iff `A/B` is, and `A/B` is never equidistant |

`2.5 · 2^-52` is `2^-50.68`. The margin is `2^-49`, so the error can sit anywhere between `2^-50.7` and
the margin; `5/2 · 2^-52` is the value used. One `f64` ULP is at most `2^-52` of the value.

`rounds_same` is the corollary the tool needs: rounding to nearest between two adjacent grid points is the
comparison with their midpoint, and `r` and `q` are on the same side of every midpoint, hence round to the same
value. I did not define round to nearest over the whole grid with ties and ranges; the corollary is for two adjacent
points and one midpoint at a time ⚠.

**Checked (v, 2026-10-31, `just lean`):** `lake build` passes, no `sorry`, and `#print axioms` of each theorem lists only
`propext`, `Classical.choice`, `Quot.sound`. The statement can fail: with `2^49` replaced by `2^48` in `margin`, or `M<2^25` by
`M<2^26`, the build fails (output in [the log](log/2026-10-31-lean-division.md)).

**What it found.** The earlier wording, "double rounding is innocuous for a quotient, since 53 >= 2*24+2" in
`spirv_exact`, and the bare `2^-49` in [`FLOAT_REPRESENTATION_202610.md`](FLOAT_REPRESENTATION_202610.md), did not
state the normal-range limit. Both are corrected. The planned proof of `margin` also needed a second case: for
`t < 0` the integer numerator gives only `1/B`; the gap is instead at least `m/2`, because `q < 2^24 <= M <= m/2`.

**Not covered.**

- **Subnormal results.** Midpoints have fewer bits (`M < 2^24`) and an exact tie can occur, so `no_tie` fails.
  `small_midpoint_ties` is a checked counterexample: `A = 1`, `B = 2`, `M = 1`, `t = 1`, `1/2 = 1/2^1`.
- Overflow, an `f32` zero, infinity and NaN operands.
- That widening `f32` to `f64` is exact (true for the formats; not proved here) and that `OpFConvert` rounds to nearest. These are assumptions about the device: the Vulkan wording was not fetched for this document ⚠.
- That a device meets 2.5 ULP. No Vulkan device has run `spirv_exact`'s output ⚠ (ADR-0005).
- Whether widening is unnecessary anywhere: no. The margin shows the `f64` route is safe, not that the plain `f32`
  division is. A 2.5 ULP `f32` division can be wrong by up to 2.5 ULP in `f32` and has no such margin.
- Any claim about Rust or SPIR-V code: the theorem is about rationals, and that `spirv_exact` implements the rewrite
  stated is read from its source, not proved.

## Risks

- A proof checks the statement, not the intent. A person reviews each statement before it is cited as evidence.
- Tooling is young. FloatSpec, a Lean port of the Flocq floating-point library, is listed on Reservoir at version 0.7.0, claims
  to compile without active `sorry`, and its roadmap lists unfinished rounding, encoding and error-bound lemmas (v, Reservoir
  page, read 2026-10-31). Lean's built-in `Float32` is a model for reasoning, not a library. So this pilot uses
  mathlib's rationals and states the rounding decision itself.
- The cache and toolchain are pinned (`VERSIONS.md`); a mathlib change can break a proof, and the fix is a new pin.
